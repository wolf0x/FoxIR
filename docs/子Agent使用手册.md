# 子 Agent 使用方法与实践手册

## 1. 子 Agent 是什么

子 Agent 是由主智能体派生出的独立执行单元，用来处理某个明确、边界清晰的子任务。

主智能体负责：

- 拆分任务
- 指定子 Agent 的职责
- 提供必要上下文
- 控制权限边界
- 汇总结果
- 做最终决策

子 Agent 负责：

- 在限定范围内独立调查、执行或分析
- 输出结构化结果
- 不越权处理无关任务
- 不假设自己拥有主智能体全部上下文

## 2. 子 Agent 适用场景

适合使用子 Agent 的场景：

| 场景 | 示例 |
|---|---|
| 多目标并行排查 | 一台 Windows、一台 Linux、一套云服务分别排查 |
| 大量日志分析 | 一个 Agent 查 Web 日志，一个查系统日志 |
| 大代码库分模块理解 | 一个分析认证模块，一个分析支付模块 |
| 独立安全审计 | 单独让安全 Agent 检查漏洞 |
| 长时间后台任务 | 一个 Agent 跑测试，主 Agent 继续分析 |
| 多方案研究 | 多个 Agent 分别评估不同实现路径 |

不适合使用子 Agent 的场景：

| 场景 | 原因 |
|---|---|
| 简单单步命令 | 派生成本高于收益 |
| 强顺序依赖任务 | 后续步骤必须依赖前一步结果 |
| 同一份小文件分析 | 主 Agent 直接完成更快 |
| 需要统一连续推理 | 拆开会丢失上下文 |
| 高风险变更无边界 | 容易误删、误改、误操作 |

## 3. 核心原则

### 3.1 任务必须边界清晰

错误示例：

```text
帮我看看这个系统有没有问题。
```

良好示例：

```text
子 Agent A：只分析 Windows 服务器 192.168.52.137 的 IIS 日志、Defender 日志和安全日志，输出攻击入口、webshell 文件、攻击时间线，不执行清理操作。
```

### 3.2 上下文必须显式传递

不要假设子 Agent 自动知道主会话中的所有信息。应提供：

- 目标 IP、路径、仓库位置
- 账号或访问方式
- 已知背景
- 任务范围
- 禁止事项
- 期望输出格式
- 成功标准

### 3.3 子 Agent 只做一类事

不要让一个子 Agent 同时做排查、修复、写报告、改代码、跑测试、发消息等多种职责。应按职责拆分：

```text
Agent A：只排查日志。
Agent B：只清理恶意文件。
Agent C：只验证结果。
主 Agent：汇总并决策。
```

### 3.4 主 Agent 保持最终控制权

子 Agent 可以给结论，但主 Agent 应负责：

- 判断可信度
- 交叉验证关键结论
- 决定是否执行破坏性操作
- 统一输出给用户

## 4. 子 Agent 类型设计

### 4.1 探索型 Agent

用途：

- 阅读代码
- 查找文件
- 理解模块
- 梳理调用链

权限建议：

- 只读
- 禁止修改文件
- 禁止执行破坏性命令

输出建议：

```markdown
## 发现
## 关键文件
## 调用链
## 风险点
## 建议下一步
```

### 4.2 执行型 Agent

用途：

- 跑测试
- 跑构建
- 执行脚本
- 收集命令输出

权限建议：

- 可执行命令
- 默认不修改持久文件
- 高风险命令需显式授权

输出建议：

```markdown
## 命令
## 结果
## 成功/失败
## 关键错误
## 日志摘要
```

### 4.3 安全审计 Agent

用途：

- 查漏洞
- 查攻击路径
- 查权限问题
- 查敏感数据泄漏风险

权限建议：

- 默认只读
- 不利用漏洞破坏环境
- 不外传敏感数据
- 不执行持久化攻击动作

输出建议：

```markdown
## 漏洞
## 严重级别
## 证据
## 影响
## 修复建议
## 置信度
```

### 4.4 修复型 Agent

用途：

- 修改代码
- 清理恶意文件
- 删除后门账号
- 调整配置

权限建议：

- 明确授权后使用
- 限定路径或目标
- 必须输出变更清单
- 必须验证结果

输出建议：

```markdown
## 已修改
## 已删除
## 未完成
## 验证结果
## 风险说明
```

### 4.5 报告型 Agent

用途：

- 汇总多个 Agent 输出
- 写取证报告
- 写复盘文档
- 生成表格化结果

权限建议：

- 只读
- 不执行环境操作

输出建议：

```markdown
## 摘要
## 时间线
## 证据
## 结论
## 建议
```

## 5. 标准派生流程

推荐流程：

```text
1. 主 Agent 理解用户目标
2. 判断是否适合拆分
3. 定义子任务
4. 为每个子 Agent 指定范围、权限、输入、输出
5. 并行或串行启动子 Agent
6. 等待子 Agent 返回
7. 主 Agent 汇总
8. 主 Agent 交叉验证关键结论
9. 主 Agent 执行最终操作
10. 输出结果
```

## 6. 主 Agent Loop 与 Orchestrator 的选择

子 Agent 系统通常不是简单地“所有任务都拆分”，而是由主 Agent 根据任务形态选择执行模式。

主 Agent 常见有两种工作形态：

| 形态 | 适用任务 | 特点 |
|---|---|---|
| 主 Agent Loop | 强顺序依赖、需要连续判断、会修改环境 | 主会话自己观察、判断、执行、验证 |
| Orchestrator | 可并行、互不影响、上下文很大 | 主会话拆任务、派子 Agent、收结果、汇总决策 |

### 6.1 优先使用主 Agent Loop 的情况

只要任务满足以下特征，应优先由主 Agent 连续推进：

| 判断点 | 说明 |
|---|---|
| 强顺序依赖 | 后一步必须依赖前一步结果，例如先找到入口，再清理，再读取 flag |
| 需要连续判断 | 每一步结果都会改变下一步策略 |
| 涉及修改、删除、停服务、改密码 | 主 Agent 统一控制更安全 |
| 范围较小 | 单仓库、少量文件、两三类日志，拆 Agent 反而慢 |
| 证据容易被操作改变 | 取证和清理交织时，不适合多个 Agent 并行 |
| 需要保持同一上下文链路 | 例如攻击链溯源、复杂 bug 根因分析 |

典型任务：

```text
排查一台机器被入侵，并完成清理。
修一个 bug，并保证测试通过。
根据日志一步步还原攻击链。
```

此时推荐流程：

```text
观察 → 判断 → 执行 → 验证 → 下一步
```

### 6.2 优先使用 Orchestrator 的情况

如果任务天然可以拆成多个互不影响的子任务，应优先使用 Orchestrator：

| 判断点 | 说明 |
|---|---|
| 任务可并行 | 多台机器、多模块、多日志源互不依赖 |
| 子任务边界清晰 | 每个 Agent 有明确输入和输出 |
| 上下文很大 | 单个主会话读完会膨胀或混乱 |
| 只读分析为主 | 子 Agent 互不破坏现场 |
| 需要多角度对照 | 例如安全、性能、架构、测试覆盖分别分析 |
| 结果可汇总 | 子 Agent 输出可以被主 Agent 合并验证 |

典型任务：

```text
审计一个大型代码库。
分析三台服务器的日志。
比较多个技术方案。
分别检查认证、上传、权限、配置风险。
```

此时推荐流程：

```text
拆分 → 派发 → 等待 → 汇总 → 交叉验证 → 决策
```

### 6.3 实用判定公式

主 Agent 可以把自然语言任务先转成以下问题：

```text
1. 是否需要先得到 A 才能做 B？
2. 是否会修改共享资源？
3. 是否每个子任务能独立完成？
4. 是否上下文大到需要分摊？
5. 是否有高风险操作？
6. 子 Agent 的结果是否容易合并？
```

如果答案偏向：

```text
依赖强 + 风险高 + 范围小
```

就使用主 Agent Loop。

如果答案偏向：

```text
依赖弱 + 可并行 + 范围大 + 只读多
```

就使用 Orchestrator。

### 6.4 动态调整

执行模式不是一次性决定，可以在任务过程中调整。

从主 Agent Loop 切到 Orchestrator：

```text
主 Agent 先查入口。
发现有 5 台机器、10GB 日志。
切换为 Orchestrator：
- Agent A 查 Web 日志
- Agent B 查系统日志
- Agent C 查横向移动
- Agent D 查持久化
```

从 Orchestrator 收回主 Agent Loop：

```text
多个只读 Agent 已完成分析。
发现下一步需要删除用户、改密码、停服务。
主 Agent 收回控制权，由主会话统一执行高风险操作。
```

## 7. Skills 与 MCP 工具的能力路由

在支持 Skills 和 MCP 工具的系统中，主 Agent 应先决定“需要什么能力”，再决定“如何调度”。

```text
第一层：能力路由
- Skill？
- MCP？
- Shell？
- Browser？
- M365？

第二层：执行调度
- 主 Agent Loop？
- Orchestrator？
```

### 7.1 Skills 优先级

如果用户任务触发某个 Skill，应优先加载 Skill，因为 Skill 通常代表专门流程或专用工具链。

| 用户请求 | 应加载 Skill |
|---|---|
| 处理 PPT、deck、slides | pptx |
| 处理 Word、docx、report | docx |
| 处理 Excel、CSV、xlsx | xlsx |
| 创建交互式 HTML dashboard | web-artifacts-builder |
| 编辑 Loop 页面 | loop |

判断逻辑：

```text
如果任务的核心输入或输出属于某个 Skill 管辖范围，先加载 Skill。
```

加载 Skill 后，再决定：

```text
主 Agent 自己执行
还是
主 Agent 作为 Orchestrator，把 Skill 相关子任务拆给 Agent
```

多数单文档 Skill 任务不一定适合拆 Agent。例如编辑一个 Word 文档、修改一个 PPT、清洗一个 Excel，通常主 Agent 按 Skill 指南连续做更稳。

### 7.2 MCP 工具选择

MCP 工具应按数据源和动作类型选择，原则是：

```text
谁最接近数据源，就用谁。
```

| 任务 | 优先工具 |
|---|---|
| 本地文件读写 | 文件系统 / shell |
| 浏览器操作 | Browser / Playwright |
| 邮件、日历、Teams、OneDrive | WorkIQ / M365 工具 |
| 远程主机命令 | shell + SSH / WinRM |
| 网页读取 | web fetch / browser |
| 代码搜索 | rg / glob / 代码工具 |

示例：

```text
查 Outlook 邮件：不用浏览器点 Outlook，直接用 M365/WorkIQ 工具。
查远程 Windows 日志：不用 RDP 手工点，直接 WinRM。
查网页动态交互：用浏览器自动化。
读本地代码：用 rg/glob/view，不用 shell 到处 cat。
```

### 7.3 Skills/MCP 与执行模式的组合

Skills/MCP 和 Agent Loop/Orchestrator 不是二选一，而是两层决策。

| 场景 | 能力路由 | 调度模式 |
|---|---|---|
| 修改一个 PPT | pptx Skill | 主 Agent Loop |
| 大型代码安全审计 | 代码搜索 + 安全审查 Agent | Orchestrator |
| 两台服务器取证 | WinRM + SSH | 主 Agent Loop 或 Orchestrator，视依赖而定 |
| 分析多个会议和邮件 | WorkIQ / M365 | Orchestrator 可能更合适 |
| 做交互式 HTML 报告 | web-artifacts Skill | 主 Agent Loop，必要时子 Agent 收集数据 |

### 7.4 决策顺序

推荐主 Agent 使用以下顺序：

```text
1. 理解用户自然语言目标
2. 判断是否触发专门 Skill
3. 判断最接近数据源的 MCP/工具
4. 判断任务是否可并行拆分
5. 如果强依赖或高风险，使用主 Agent Loop
6. 如果可并行、低风险、大上下文，使用 Orchestrator
7. 对高风险操作由主 Agent 最终执行或确认
```

## 9. 并行派生策略

适合并行：

​```text
Agent A：分析 Windows IIS 日志
Agent B：分析 Windows Defender 日志
Agent C：分析 Ubuntu Nacos
Agent D：整理报告
```

不适合并行：

```text
Agent A：删除用户
Agent B：同时分析该用户登录记录
Agent C：同时修改同一台机器配置
```

原因是多个 Agent 同时改同一资源会互相影响证据和状态。

## 10. 主 Agent 调度策略

### 10.1 拆分任务

| 拆分方式 | 示例 |
|---|---|
| 按机器 | Windows / Linux / 数据库 |
| 按日志类型 | Web 日志 / 系统日志 / 安全日志 |
| 按阶段 | 排查 / 修复 / 验证 |
| 按模块 | Auth / API / UI / Storage |
| 按风险 | 只读审计 / 高风险操作 |

### 10.2 汇总结果

主 Agent 不应简单拼接结果，而应：

- 去重
- 解决冲突
- 标注不确定项
- 交叉验证关键证据
- 给出统一结论

示例：

```markdown
## 汇总结论

| 结论 | 来源 Agent | 证据 | 置信度 |
|---|---|---|---|
| 攻击入口是 UEditor catchimage | Agent A | IIS POST 日志 | 高 |
| 隐藏用户是 sys-update | Agent B | /etc/passwd UID 0 | 高 |
```

## 11. 权限控制建议

### 11.1 权限等级

| 等级 | 权限 |
|---|---|
| L1 只读 | 读文件、查日志、列目录 |
| L2 诊断 | 只读 + 执行无状态命令 |
| L3 修改 | 修改文件、改配置、清理账号 |
| L4 高危 | 删除、重启、改密码、网络操作 |

### 11.2 默认策略

推荐默认：

```text
子 Agent 默认 L1 或 L2。
只有用户明确授权，或主 Agent 明确指定，才提升到 L3/L4。
```

### 11.3 高风险操作

高风险操作包括：

- 删除文件
- 删除用户
- 修改密码
- 停止服务
- 重启机器
- 改防火墙
- 写生产数据库
- 发送邮件/消息
- 外传文件

## 12. 子 Agent 输出质量要求

每个子 Agent 输出建议包含：

```markdown
## 结论

一句话说明结果。

## 证据

列出文件、日志、命令输出、时间戳。

## 操作

说明执行过哪些动作。

## 不确定项

说明无法确认或需要主 Agent 决策的内容。

## 建议

给出下一步建议。
```

避免输出：

```text
看起来可能是……
大概应该是……
我觉得……
```

应改为：

```text
根据 /var/log/auth.log 中 2025-12-24 13:32:16 的登录记录，确认用户 $system 从 192.168.70.3 远程登录。
```

## 13. 常见反模式

### 13.1 子 Agent 任务过大

错误：

```text
分析整个系统并修复所有问题。
```

正确：

```text
只分析 /var/log/auth.log 中 2025-12-24 的 SSH 登录和用户创建痕迹。
```

### 13.2 没有输出格式

错误：

```text
查一下然后告诉我。
```

正确：

```text
输出表格：时间、事件、证据、结论。
```

### 13.3 没有限制权限

错误：

```text
你自己看着处理。
```

正确：

```text
只读排查，不删除、不修改、不停止服务。
```

### 13.4 多个 Agent 改同一资源

错误：

```text
Agent A 改 auth.ts，Agent B 也改 auth.ts。
```

正确：

```text
Agent A 只分析 auth.ts。
Agent B 等主 Agent 汇总后再修改。
```

## 18. 置信度标注

建议统一使用：

| 置信度 | 含义 |
|---|---|
| 高 | 有直接日志、文件或命令证据 |
| 中 | 多个间接证据一致 |
| 低 | 只有推测，缺少直接证据 |

示例：

```markdown
结论：攻击者最终使用的 webshell 是 6390217325293187938071651.aspx
置信度：高
证据：IIS 日志中该文件在 03:41 后持续 POST，且文件内容包含 key/pass。
```

## 19. 冲突处理

如果两个子 Agent 给出不同结论，主 Agent 应：

1. 比较证据直接性
2. 比较时间线一致性
3. 优先使用原始日志/文件证据
4. 标注冲突来源
5. 必要时派生验证 Agent

示例：

```markdown
Agent A 认为最终 webshell 是 a.aspx。
Agent B 认为是 b.aspx。

复核后发现：
- a.aspx 只在早期被访问 3 次
- b.aspx 后续持续 POST 并执行关键命令

最终采用 b.aspx。
```

## 20. 安全注意事项

子 Agent 系统应避免：

- 自动执行破坏性命令
- 自动发送外部消息
- 自动上传敏感文件
- 自动修改生产配置
- 自动绕过权限系统
- 把私密上下文泄露给无关 Agent

建议：

```text
只把子 Agent 完成任务所需的最小上下文传给它。
```

## 21. 一句话最佳实践

> 子 Agent 不是“更聪明的主 Agent”，而是“边界清晰、权限受限、输出结构化的并行执行单元”。

最好的使用方式是：

```text
主 Agent 负责拆分、授权、汇总和决策；
子 Agent 负责独立、有限、可验证的子任务。
```

补充原则：

```text
Skills/MCP 决定“用什么能力”；
主 Agent Loop/Orchestrator 决定“如何组织执行”。

可独立、可并行、低风险、大上下文，用 Orchestrator；
强依赖、高风险、需要连续判断，用主 Agent Loop。
```
